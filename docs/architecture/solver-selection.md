# Solver selection guide

Every rung of the ladder is measured on the same committed graphs, so the choice
between them is a lookup, not an opinion. Numbers come from
`docs/benchmarks/routing-city.md` (104,991 nodes) and
`docs/benchmarks/routing.md` (2,405 nodes), both regenerated by
`scripts/bench/routing_benchmark.py`.

## The rule in one paragraph

Route once, pay nothing up front: use A*. Route many times on the same graph:
pay for contraction once and use CH. Need a lower bound you can trust on a graph
you have not preprocessed: use ALT. Need an answer fast and approximate: use
weighted A\*. Need an exact multi-stop order for a handful of stops: use
Held-Karp. Anything larger: 2-opt from nearest neighbor, and report the gap.

## Point-to-point

| Situation | Solver | Why | Evidence |
| --- | --- | --- | --- |
| One route per process, small or medium graph | A\* (`astar-haversine`) | No preprocessing; admissible straight-line bound | Centro: 671 expansions vs Dijkstra's 1,098 (200 pairs) |
| Large graph, no time to preprocess | ALT (`astar-alt`) | Landmarks cost seconds and cut expansions by an order of magnitude | City: 5.9% of the graph, 64 ms; preprocessing ≈4.3 s |
| Many routes on one graph (dispatch, ETAs, batch pricing) | CH (`contraction-hierarchy`) | Two upward searches touch a few dozen nodes | City: 85 expansions (0.1%), 2.04 ms; break-even 13 queries vs A\*, 35 vs ALT |
| Latency budget below exact search, quality negotiable | Weighted A\* (`weighted-astar-eps*`) | f = g + ε·h; bounded to ε× the optimum | City ε=5: 13.8% of the graph, max 13% over; ε=1.5: 37.7%, max 0% observed |
| You need every destination at once (cost matrix, reachability) | One-to-all Dijkstra (`distances_from`) | A\* wins for one target, Dijkstra for all of them | City batch matrix: 7 stops in ≈1.7 s |

Two honest caveats the table encodes:

* **A\* is not automatically faster than Dijkstra.** On one-way streets the
  straight-line bound is weak, and on the city graph A\* expands 17% fewer nodes
  than Dijkstra yet takes 35% longer in wall time. The heuristic is only worth
  its cost when it prunes aggressively.
* **Bidirectional search is exact but slow in CPython.** Two heaps and two
  potential lookups per relaxation made it 3.5× slower than plain Dijkstra on
  the city graph (435 ms vs 123 ms) despite expanding fewer nodes. It stays in
  the lab as a measured comparison, not as a recommendation.

## Multi-stop

| Situation | Solver | Why | Evidence |
| --- | --- | --- | --- |
| 2–3 orders, ≤ 7 stops, pickup-before-dropoff | Held-Karp with precedence | Exact, bounded, microseconds | 7 stops: 486 evaluations, 0.2 ms; 18% shorter tour than nearest neighbor |
| Up to 13 stops | Held-Karp | Still exact, still fast | 13 stops: 135,180 evaluations, ≈40 ms |
| Beyond the exact bound (14+ stops) | 2-opt from nearest neighbor | Fast, no guarantee; report the gap | 13 stops on graph costs: 2-opt reaches the optimum here, but that is luck, not a guarantee |
| Monotone, cheap first guess | Nearest neighbor | O(n²) and easy to explain | 7 stops: 21 evaluations, 21% longer than exact |

The exact cap exists for a reason: 14 stops is 87 billion permutations, and the
roadmap forbids unbounded factorial work inside a request.

## Decision flow

```text
Need a route?
├─ one route, no preprocessing budget ........ A*
├─ many routes on the same graph
│   ├─ build time available (seconds) ....... CH   (break-even ~76–209 queries)
│   └─ build time not available ............. ALT
└─ quality can slip, latency cannot .......... weighted A* (report ε)
Need an order over stops?
├─ ≤ 13 stops, exact ........................ Held-Karp (+ precedence)
└─ more stops ............................... 2-opt from nearest neighbor
Need costs between many stops?
└─ one-to-all Dijkstra per stop ............. n runs, not n²
```

## Why the product uses A*

The courier flow plans one route per delivery on the 2,405-node centro graph:
A* answers in about a millisecond with no build step. Shipping CH in the product
would add seconds of startup and a cache to invalidate for no user-visible gain.
The guide is the place where that changes: a dispatch service that prices
thousands of ETAs per minute should build the hierarchy at boot and use CH, which
is exactly what the break-even table quantifies.

## Reproducing

```bash
python scripts/bench/routing_benchmark.py --graph city     # docs/benchmarks/routing-city.*
python scripts/bench/routing_benchmark.py                  # docs/benchmarks/routing.*
python scripts/bench/routing_benchmark.py --smoke          # CI gate
```

Every artifact records the graph version, the machine and the commit it was
generated from, and the work-bound tests in `tests/routing/` pin the expansion
budgets so a regression is a failing test rather than a surprise in a demo.
