# Routing contract

Routing consumers depend on `RouteProblem`, `RouteResult`, and the `RouteSolver`
protocol instead of a concrete algorithm. `RouteProblem` is a validated, immutable
complete cost matrix with at least two labels and a valid origin index. Costs must be
finite, numeric, and non-negative.

`RouteResult` reports a closed ordered `route`, its `total_cost`, the `solver_name`,
`execution_time_ns`, and `routes_evaluated`. A solver may include `route_history`
only for bounded experiments; consumers must treat it as optional.

## The legacy baseline

`LegacyBruteForceTSPSolver` is the algorithm from the coursework exercise that started this repository:
try every ordering, keep the cheapest. It is deliberately retained, and not only as a comparison.

- **Correctness oracle.** Every exact replacement (Held-Karp, 2-opt, the windowed VRP) is asserted
  against it on small matrices, because an exhaustive search is hard to get subtly wrong.
- **Published baseline.** It is the reference row in [the benchmark table](../benchmarks/routing.md),
  so "the new solver is better" is a measured claim rather than an adjective.
- **The demo's first router.** In the fictional company's history this is the legacy system it
  outgrew: the class is named `Legacy…`, the benchmark table doubles as the migration memo, and this
  page is the contract note explaining why it was replaced. A coursework algorithm about
  combinatorial explosion became an in-world piece of technical debt.

It fixes the route origin at index zero, covers solver computation only, and excludes rendering,
networking, and other application work. See [the origin story](../origin.md) for why it stayed.

## M1 delivery-route extension

The matrix contract above remains the legacy/algorithm-laboratory contract. M1 adds a
separate shortest-path contract rather than pretending that a cost matrix is a road
graph:

| Contract | Required fields | Result |
| --- | --- | --- |
| `PathProblem` | graph ID/version, origin node, destination node, cost assumptions | validated graph traversal input |
| `PathResult` | ordered nodes, geometry, distance, estimated seconds, solver/version, nodes expanded | one route segment |
| `DeliveryRouteProblem` | courier origin, restaurant pickup, customer drop-off, graph/version, deterministic seed | two-leg delivery input |
| `DeliveryRouteResult` | ordered stops, route segments, GeoJSON geometry, distance/ETA, solver/version, metrics, warnings | provider-neutral route consumed by courier/map surfaces |

## Solver ladder

The live product route uses plain A* (no preprocessing). The lab and the
benchmark harness compare every rung on the same problem and the same graph:

| Solver | Contract name | Preprocessing | Guarantee | Measured (200 pairs, time objective) |
| --- | --- | --- | --- | --- |
| Dijkstra | `dijkstra-oracle` | none | exact | centro 1,098 (45.7%); city 53,885 (51.3%) |
| A* (straight line) | `astar-haversine` | none | exact | centro 671 (27.9%); city 44,759 (42.6%) |
| ALT (landmarks) | `astar-alt` | ~41 ms centro / ~3.0 s city | exact | centro 378 (15.7%); city 6,186 (5.9%) |
| Bidirectional + ALT | `bidirectional-alt` | same table | exact | centro 706 (29.4%); city 19,272 (18.4%) |
| Weighted A* | `weighted-astar-eps*` | none | ≤ ε × optimal | ε=1.5: centro 544 (22.6%), max 0.16% over |
| Contraction hierarchy | `contraction-hierarchy` | ~1.6 s city (138 MB) / <0.1 s centro | exact | city 85 (0.1%), 1.45 ms/query |
| Time-dependent Dijkstra | `td-dijkstra` | none (profile is data) | exact under FIFO | oracle for `td-astar`; Bellman-Ford differential |
| Time-dependent A* | `td-astar` | none | exact under FIFO | used by the planner when a departure time is present |

Time-dependent solvers take a `departure_at` (epoch seconds) and the traffic
profile, and return `arrival_at` alongside the usual fields. The profile is
`data/graph/traffic-profile.json`; it is validated for FIFO at load time and a
flat profile reduces these solvers exactly to their static counterparts.

Numbers live in `docs/benchmarks/routing.md` and are regenerated by
`scripts/bench/routing_benchmark.py`. Every exact solver must agree with the
oracle on cost — `tests/routing/test_informed_solvers.py` and
`tests/routing/test_osm_graph.py` assert it, and the weighted variant is the
only one allowed to overshoot.

## Multi-stop and constraints

Tours are solved by `routing/tsp.py` (order only) and `routing/vrp.py` (order + capacity + windows +
precedence). The planner uses the VRP path for batches: stops carry a signed volume, a service time
and an optional drop-off window, windows are priced softly and enforced by `max_lateness_seconds` at
acceptance, and `ExactWindowSolver` is used up to 8 stops (insertion + local search above that).
Dynamic re-plans accept `picked_up` deliveries, which contribute a drop-off only and start the tour
with their volume already on board.

## Street graph

Two real extracts share one schema and one set of build rules (`scripts/data/osm_graph.py`):

| Artifact | Size | Role |
| --- | --- | --- |
| `data/graph/sao-paulo-centro-osm.json` | 2,405 nodes / 3,431 edges, 0.7 MB | Product and lab: fast reads, browser-renderable, deterministic demo geometry |
| `data/graph/sao-paulo-city.json.gz` | 104,991 nodes / 177,114 edges, 2.1 MB gzipped (compact-v1) | Benchmark and dispatch scale: CH preprocessing, city-wide queries |
| `data/graph/sao-paulo-centro.json` | 77 nodes | Synthetic fixture for unit tests and the offline fallback |

`load_graph` reads `.json` and `.json.gz` transparently and dispatches on
`"format": "compact-v1"` (index-aligned ids/nodes/edges) versus the
object-per-node documents. `ROUTING_GRAPH_PATH` selects the graph; without it
the container prefers the centro extract, then the synthetic lattice, then
straight-line routing.

The builder keeps **only the largest strongly connected component** of the
directed graph: central São Paulo is one-way-dominant (76% of ways), so much of
the network can be entered but not left. Contracting degree-2 chains and
filtering measured: 16,816 raw nodes → 9,058 junctions → 2,405 in the largest
component. Coordinates are rounded before distances are measured and distances
are ceiled to 0.1 m, so every stored edge is at least the straight line between
the stored coordinates — the condition the A* heuristic needs to stay
admissible.

Cost matrices (`routing/matrix.py`) run one-to-all Dijkstra from each stop
(n runs) rather than A* per ordered pair (n² runs): A* wins for one
destination, Dijkstra wins when every destination is needed. Batch dispatch
composes the two contracts — matrix for pricing, `RouteSolver` for ordering
under precedence — and dispatch assignment stays out of the shortest-path
contract.
