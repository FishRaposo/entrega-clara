# M1 API and event contract

**Status:** Planned contract for implementation
**Version:** `v1`
**Product:** Entrega Clara
**Related:** [M1 design](../superpowers/specs/2026-09-01-milestone-1-core-delivery-loop-design.md), [provider boundaries](provider-and-integration-boundaries.md), [M1 runbook](../runbooks/milestone-1-development.md)

This is the implementation-facing contract for the M1 HTTP and realtime surface. It describes the shape that clients and tests should target; it does not claim that these endpoints are already implemented in the current scaffold.

## Contract principles

- Base path: `/api/v1`.
- JSON for request/response bodies.
- OpenAPI generated by FastAPI is the machine-readable contract.
- Commands are explicit operations, not a generic `PATCH /orders/{id}/state`.
- The server is authoritative for identity, ownership, totals, state, and payment outcome.
- Successful commands return the changed resource or a command result with its aggregate version.
- Failed commands return the safe error envelope.
- State changes are idempotent where retries are expected.
- List endpoints are bounded and pagination-compatible.
- SSE is for server-to-client updates; commands remain HTTP.

OpenAPI is a language-independent interface description. See the [OpenAPI 3.1.1 specification](https://spec.openapis.org/oas/v3.1.1.html).

## Identity context

The API resolves an `IdentityContext` before an application service runs. In M1, a development-only demo identity mechanism may select a server-known identity. The exact transport can be a header or local cookie, but it must be isolated behind the identity resolver and disabled outside demo mode.

The client must never be able to grant itself a role by sending `role=admin`. Authorization checks the resolved identity against the resource:

| Actor | Allowed M1 scope |
| --- | --- |
| Customer | Own cart, seeded addresses, own orders, own notifications/tracking |
| Restaurant operator | Orders belonging to their restaurant; confirmation/preparation actions |
| Courier | Own availability, offers, active delivery, location, pickup/completion |
| Operations | Read-only operational projections and demo controls |

Every denied response is safe and does not reveal whether an unrelated resource exists when that distinction would expose private information.

## Customer commands

### Add cart item

```http
POST /api/v1/me/cart/items
Content-Type: application/json

{
  "menu_item_id": "menu_item_demo_001",
  "quantity": 2,
  "observation": "Sem coentro"
}
```

The server validates availability, quantity, restaurant/cart compatibility, observation length, and current menu price. The response contains the authoritative cart totals.

### Update/remove cart item

```http
PATCH /api/v1/me/cart/items/cart_line_demo_001
Content-Type: application/json

{
  "quantity": 1,
  "observation": "Pouco sal"
}
```

Removal uses `DELETE /me/cart/items/{line_id}`. A zero quantity is represented by removal, not an ambiguous update.

### Apply coupon

```http
POST /api/v1/me/cart/coupon
Content-Type: application/json

{
  "code": "BEM-VINDO-DEMO"
}
```

The response includes the recalculated subtotal, discount, fees, and total. An invalid, expired, ineligible, or already-used code produces `coupon_invalid` or a more specific stable error code and does not mutate the prior total.

### Checkout

```http
POST /api/v1/me/orders/checkout
Idempotency-Key: checkout-demo-001
Content-Type: application/json

{
  "address_id": "address_demo_001",
  "payment_method": "pix"
}
```

The server snapshots cart lines and prices, validates the address/coupon/payment request, creates one order and one payment attempt, and commits them atomically. A repeated request with the same key and equivalent body returns the original result. A different body with the same key returns `idempotency_conflict`.

## Restaurant commands

| Method | Path | State effect |
| --- | --- | --- |
| `POST` | `/restaurant/orders/{order_id}/confirm` | `placed → confirmed` |
| `POST` | `/restaurant/orders/{order_id}/prepare` | `confirmed → preparing` |
| `POST` | `/restaurant/orders/{order_id}/ready` | `preparing → ready_for_pickup` |

The application verifies the operator owns the restaurant before applying a transition. A generic state mutation endpoint is not allowed.

## Courier commands

| Method | Path | State/effect |
| --- | --- | --- |
| `PUT` | `/courier/availability` | Set current courier available/unavailable |
| `POST` | `/courier/deliveries/{delivery_id}/accept` | Assign courier and order `courier_assigned` |
| `POST` | `/courier/deliveries/{delivery_id}/pickup` | `courier_assigned → picked_up` |
| `POST` | `/courier/deliveries/{delivery_id}/start` | `picked_up → en_route` |
| `POST` | `/courier/deliveries/{delivery_id}/location` | Append monotonic tracking event |
| `POST` | `/courier/deliveries/{delivery_id}/complete` | `en_route → delivered` |

The courier can have only one active M1 delivery. Location payloads must contain a sequence and coordinates bounded by the selected graph/market policy:

```json
{
  "sequence": 4,
  "latitude": 12.3456,
  "longitude": -45.6789
}
```

The example coordinate is synthetic and illustrative only; public fixtures must use synthetic/generalized data.

## Demo commands

The existing deterministic controls remain namespaced:

| Method | Path | Effect |
| --- | --- | --- |
| `GET` | `/demo/scenario` | Current scenario snapshot |
| `POST` | `/demo/reset` | Reset selected scenario only |
| `POST` | `/demo/advance` | Advance the scenario through application commands |
| `POST` | `/demo/clock` | Advance deterministic time |

Demo controls cannot write repository state directly. They invoke the same command handlers used by role surfaces.

## Response conventions

Successful resource responses should include stable IDs, canonical UTC timestamps, market/currency where money is present, and an aggregate `version` when the resource is mutable.

Money uses integer minor units:

```json
{
  "subtotal_minor": 4590,
  "discount_minor": 500,
  "delivery_fee_minor": 800,
  "total_minor": 4890,
  "currency": "BRL"
}
```

The domain owns rounding and totals. The browser formats the result for `pt-BR`; it does not recalculate the order.

## Error contract

```json
{
  "type": "https://entrega-clara.example/errors/coupon-invalid",
  "title": "Coupon cannot be applied",
  "status": 422,
  "code": "coupon_invalid",
  "detail": "The coupon is not valid for this cart.",
  "field_errors": {},
  "correlation_id": "cor_demo_001"
}
```

The hostname is a placeholder until a canonical public error namespace is selected. The shape is stable; localized copy and details may evolve. Never return SQL, stack traces, provider bodies, credentials, internal paths, or full personal data.

Recommended status classes:

| Status | Use |
| --- | --- |
| `400` | Malformed command shape |
| `401` | Missing/invalid future session |
| `403` | Identity lacks scope |
| `404` | Authorized resource not found |
| `409` | State/version/idempotency conflict |
| `422` | Valid shape but domain rule rejected |
| `429` | Rate limit |
| `503` | Explicit provider/persistence unavailable state |

## SSE contract

`GET /api/v1/orders/{order_id}/stream` returns `text/event-stream` after authorization. The first event is a snapshot; later frames carry committed events.

Example event envelope:

```json
{
  "id": "evt_demo_004",
  "type": "delivery.en_route",
  "aggregate_type": "order",
  "aggregate_id": "order_demo_001",
  "actor_id": "courier_demo_001",
  "actor_role": "courier",
  "correlation_id": "cor_demo_008",
  "sequence": 8,
  "occurred_at": "2026-09-01T12:00:08Z",
  "payload_version": 1,
  "payload": {
    "order_status": "en_route"
  }
}
```

The SSE framing should use `id`, `event`, and `data`. Clients must handle reconnect, `Last-Event-ID`, snapshot reconciliation, heartbeat, and an unavailable stream. M1 does not promise lossless replay from the in-process hub; that promise begins only after a durable outbox/event log is introduced.

## Compatibility rules

- Add fields compatibly when possible; do not silently change field meaning.
- Version event payloads independently from route URLs.
- Keep enum values stable and document deprecations.
- Treat provider statuses as adapter input, never public domain enum values.
- Preserve `idempotency_key` behavior across deploys in persistent mode.
- Add contract tests before changing an endpoint used by another role.
- Update OpenAPI, frontend types, tests, traceability, and docs together.

## Contract test checklist

- [ ] Every listed endpoint has request/response schema coverage.
- [ ] Error envelope is stable for domain, persistence, and provider failures.
- [ ] Role/ownership tests cover allowed and forbidden commands.
- [ ] Checkout idempotency and conflict behavior are tested.
- [ ] Money is integer minor units and currency-aware.
- [ ] Event IDs, versions, sequences, and correlation IDs are present.
- [ ] SSE first response is a snapshot and reconnect reconciles it.
- [ ] Map/provider outage does not block core commands.
- [ ] OpenAPI is generated and reviewed in CI.
