# The evidence spine

A portfolio claim is only worth what its artifact shows. The evidence spine is the set of committed
files that make each claim checkable by a stranger in minutes. Build it before writing prose.

## Artifact types

| Artifact | Best for | Shape |
| --- | --- | --- |
| Benchmark result (JSON + Markdown + chart) | Performance and algorithm claims | Machine-readable results plus a human table, generated by one command |
| Test suite | Correctness claims | Differential tests against a simple oracle; named in the README |
| Verification record | "Everything passes" claims | One table: gate, command, last result, scope notes |
| ADR / decision record | Judgment claims | Context, decision, measured consequences, rejected alternatives |
| CI run | "It works on a clean machine" claims | Green default branch; matrix on the platforms you claim |
| Replay trace / media | Visual or interactive claims | Committed trace, generated GIF/video/screenshot |
| Live demo | Product-shaped claims | Seedable, rate-limited, no login for the reviewer |

## Measurement rules

1. **Name the workload.** Denominator, sampling method, seed and environment. "200 pairs sampled
   with seed 20260901 on the committed graph" is checkable; "fast" is not.
2. **Report a distribution, not a hero number.** Median plus worst case; include the share of the
   graph or the share of runs when it makes scale visible.
3. **Prefer work to time.** Expansions, operations, allocations and bytes are stable across machines.
   Wall time is useful but noisy; report both and never compare across machines.
4. **Report preprocessing separately.** Anything paid once (index build, landmark table, compilation)
   gets its own line, plus the **break-even** against the no-preprocessing baseline.
5. **State the baseline.** Every "better" needs a "than". Compare on the same matrix, graph or input.
6. **Use an oracle.** A slow, obviously-correct implementation (Dijkstra, brute force, exhaustive
   enumeration) that the fast one must match. Differential tests are the cheapest credibility you can
   buy.
7. **Record the machine.** OS, CPU class, runtime version, commit hash; stamp generated artifacts with
   `commit-dirty` when the tree is not clean.
8. **Never hand-edit generated output.** The generator is the source of truth; a freshness gate in CI
   catches drift.

## Worked numbers (Entrega Clara, city graph)

| Claim | How it is backed |
| --- | --- |
| CH answers in 85 expansions / 2.82 ms vs Dijkstra 53,885 / 172 ms | `docs/benchmarks/routing-city.md`, generated by `scripts/bench/routing_benchmark.py --graph city` |
| Preprocessing costs 2.7 s and 138 MB, breaking even at 12 queries vs A\* | Same artifact; memory measured in a second untimed build |
| ALT expands 5.9% of the graph | Same artifact plus `tests/routing/test_informed_solvers.py` |
| Exact solvers agree with the oracle | Differential suites in `tests/routing/` |
| Batches respect capacity and windows | `tests/routing/test_vrp.py`, `tests/api/test_batching.py`, ADR 0011 |

Note what makes the table usable: a denominator (200 pairs), a baseline (Dijkstra or A\*), a stable
work metric (expansions), a separate cost line (preprocessing), and a decision number (break-even).

## Claim-to-artifact audit

For each sentence in the README that contains a number, a superlative or a guarantee:

1. Write the claim in one line.
2. Name the artifact that proves it, or the command that regenerates it.
3. If neither exists: measure it now, soften it to what is true, or delete it.

Common unbacked claims: "production-ready", "blazing fast", "scales to millions", "used by N users",
"fully tested". Replace each with a measured statement or remove it.

## Artifact lifecycle

- **Generate** in the same change that alters behavior.
- **Commit** the output so reviewers do not need to run anything to see the numbers.
- **Gate** regeneration in CI: regenerate and fail if the committed copy changed.
- **Date** external-data snapshots (OSM extract, traffic profile, dataset) and document how to refresh
  them.
- **Retire** numbers that no longer reproduce; a stale benchmark is worse than none.

## Anti-patterns

- Benchmark tables with no denominator or baseline.
- A single "best run" time presented as the expected performance.
- Wall-clock comparisons across different machines or languages.
- Tests that only assert "no exception" for a correctness-critical algorithm.
- A verification table that says "pass" for checks that were skipped.
